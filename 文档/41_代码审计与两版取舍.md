## 4. 附带代码审计

### 4.1 文档37的Python提取器

文件：`参考代码与AI音乐工作流/extract_music_dna_workflow.py`。

- **实际AST检查失败：** 第105行 `unterminated string literal`；多处字符串中的换行破坏Python语法。
- WAV路径只是8等分RMS和一段FFT的谱峰/谐波邻域，节奏、包络参数与旋律模板大量为硬编码；不能称“提取完整8小节乐谱”。
- 对复调混音选最大谱峰不能可靠识别某一乐器基频及泛音比例；分析含义不足以支持原承诺。
- 短音频的切片长度可能与Hanning窗口长度不一致，需补边界处理。
- JSON路径也缺少schema/枚举/范围验证；直接把style_id拼成代码常量名有标识符风险。

处理：保留原件，不作为生产工具。M80用现有真实参考profile编写更小且严格的数据桥接。

### 4.2 文档38的Python桥接器

文件：`参考代码与音乐分析桥接/bridge_music_analyzer_to_score.py`。

- **实际AST检查失败：** 第102行 `unterminated string literal`。
- 读取summary/essentia/timeline，但未读取宣称使用的beats.csv。
- 将时长六等分后分类，属于启发式建议，不等于乐段识别；和文档36的12秒窗口/具体边界也不是同一划分。
- 输入字段路径写死；对空CSV、非数值列、缺字段和标量/数组差异缺少验证。
- 返回的内容为统计与建议，未生成逐音旋律、逐和弦顺序，也没有实际输出承诺的低通截止频率/完整配器谱材。
- `target_active_onset_rate`强制至少2.2会把稀疏参考也推成密集风格，与静谧目标矛盾。

处理：不把“修好字符串”视为修好了分析能力。将统计输入与原创谱材拆开，按真实schema接入。

### 4.3 两个GDScript引擎参考

文件：`city_creation_living_melody_engine_ref.gd`和`city_creation_multistyle_chamber_engine_ref.gd`。本次进行了静态阅读，**没有运行Godot解析或播放**。

- 可借鉴乐句数组、风格配器表和段落意图，但它们不是能替换当前生产模块的完整补丁。
- 两者的 `fit_pitch_smooth`是逐音选择，并非整句优化；最后clamp不一定保持调式音级。
- 调用旧 `score_script.note()`仍会fold，因此前面设置的放宽音域/低音段不一定保留。
- 第二份六风格表提供melody_bars，但文件的主要函数是琶音生成与段落字典；没有完整将这些旋律接入现有lead/roles/cache/player的链路。
- 琶音步长为 `2.76/subdiv`，加0.12秒起点，不能保证落在80BPM的0.1875秒网格。例如subdiv=8时步长0.345秒，不是标准八分0.375秒。
- 把deep_climax的target_layer改成1，会混淆“伴奏低音”与“低音领唱”的职责；实际输出仍受旧BOUNDS和note路径约束。
- 原声部切换、首次播放、导出stamp、缓存组合规模、夜曲和short cue路由不在参考实现中完整处理。

处理：只摘取经过核对的内容思想，按M78～M80生产契约重新实现；不直接并入仓库。
