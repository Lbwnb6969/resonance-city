## 开始与事实核对

先执行 `python tools/audit_creation_workspace.py --check-remote`，读取 AI_START_HERE.md、PROJECT.md、AGENTS.md。backlog 只读 holistic_integration.current_construction_spec、首个未通过轮次及其相关 next_step；按需读日志末30行。再读取四专题最终统一工程审查与收口总案及本子步对应章节，不全量加载历史。

区分当前源码、验证证据、设计提案和历史记录。外部参考包的 index_only 不代表本地没有源码；先查本地正文。设计案中的旧 Schema、待实现、冻结列表不能覆盖较新的真实成果。遇到冲突先查相关源码和记录，说明采用依据；只有无法由现有证据解决、且影响产品方向的冲突才询问用户。

核对 HEAD、远端、脏文件和本子步已有实现。远端不可达如实记录，本地施工继续；当前暂停上传，不重试推送。别人的在途改动不覆盖、不混入提交；同一功能正被另一会话修改时，先核对归属和已有成果，不重复实现。

## 每个施工子步

1. 从当前真实首步选一个可验证的玩家目标，写清完成条件、涉及文件和最低充分验证。不得直接跳到总案 P0 重做已完成内容。
2. 修改前核对 Git 备份；已有本轮独有未提交成果先备份，其他会话修改保留原状。重要文件需退出时移入专门废弃批次，核依赖和哈希，不直接删除。
3. 沿用现有模式，实现最简单可行方案；新逻辑职责清晰。保留个人作品、旧档、Undo/Redo、历史权益及公共 API。
4. 做能证明目标成立的最小验证。代码按风险选 CPU/API、隔离旧档、真实 OpenGL 输入或 PCM；使用 --isolated-session、persistence=false，作品目录放验证记录。文档轮只跑链接和 Harness。
5. 只有证据成立才更新 PROJECT/backlog/日志，不另建竞争进度；日志每轮不超过6行。审阅本轮 diff，只提交本轮文件或确属本轮的片段，本地 Git 备份后交付。

## 避免过度防御和低价值打磨

只为明确输入边界、真实失败和数据完整性增加校验。不要为假设中的未来需求加配置层、通用框架、多级回退、重复状态或吞错逻辑；不能以此为理由删除现有必要兼容和验证。

目标已满足且相关检查通过就结束该子步。不要追加同义测试、穷举无关组合、纯命名重构或无测量依据的优化。继续修复须说明新增证据、真实玩家影响或具体阻塞；没有这些依据的美化记入后续，不延长当前轮。

同一问题连续两次尝试没有新增证据时，停下重复试改，重新定位根因或缩小方案，记录阻塞与下一次可验证动作。数据损坏、崩溃、核心不可用必须修复；低影响尾项不阻塞已达成的独立目标。每完成一个子步重新核对首步，不擅自换专题，也不困在局部无限打磨。

## UI 稳定约束

沿用现有视觉语言、五画具导航、选屋编辑、J/L/F1和作品馆职责。改 UI 前明确哪个玩家操作失败或不可发现，只修改对应路径；不顺手换布局、配色、字号、快捷键或术语，不新增重复入口。

必须调整布局时复用已有组件与定位规则；验证实际窗口中的入口可发现性、遮挡、点击、关闭/返回及相关快捷键。新设计中的尺寸和容器假设先与真实实现核对。禁止把必要状态解释藏掉，也禁止把调试信息塞进普通玩家流程。
